# EP-17.05: Hash-chained audit trail

## 1. Identification
- **Epic:** [EP-17](README.md)
- **Priority:** P0
- **Dependencies:** 17.01 (uses the actor from 17.04 when available)
- **Blocks:** 17.06, 17.07, 17.10

## 2. Context
About 89 mutating routes exist (`ui/server/router.js:117-206`, `ui/server/routes/*.routes.js`); several run commands or write outside ROOT. The closest audit today is `global/deploy-actions.jsonl` with a client-supplied `actor` (`deploy-actions.service.js:84-143`). Event retention would prune audit rows (`event-retention.js:19-25`). Whether the PIN check covers every mutating route is unverified. See [ADR-013](../../03-decisions/ADR-013-identidade-rbac-auditoria.md).

## 3. Objective
Every mutating action, and every denied attempt, leaves one verifiable audit row with who, what, where and outcome.

## 4. Requirements
**Functional**
- RF1: table `audit_log` as in ADR-013 (actor, actor_kind, on_behalf_of, project_id, action, resource_type, resource_id, outcome, request_id, ip, before_hash, after_hash, detail, prev_hash, hash). Triggers reject UPDATE and DELETE.
- RF2: `ui/server/audit/audit-writer.js` computes `hash = sha256(prev_hash + canonical(row))` inside the caller's transaction; a `request_id` is assigned per request.
- RF3: a route-table wrapper audits every non-GET route automatically with `action = METHOD route-pattern`; services add domain detail through `ctx.audit.record(...)`.
- RF4: `GET /api/audit/log` (paged, filtered by actor, project, action, date) and `node tools/audit.js verify` that walks the chain and reports the first broken row.
- RF5: `detail` is redacted (secrets, e-mail, CPF, phone); content bodies are never stored, only identifiers and hashes.
- RF6: legacy `deploy-actions.jsonl` imported as `actor_kind=legacy`.
- RF7: modes `off|observe|enforce-write` so failures to write audit can block the action in `enforce-write`.

**Non functional**
- Audit write cost under 2 ms per request; exempt from every retention sweep; files under 300 lines.

## 5. Architecture
`ui/server/audit/` (writer, redaction adapter, route wrapper) and `ui/server/db/repos/audit.repo.js`. First task is a route-coverage test that lists every mutating route and fails if one is not wrapped.

## 6. Implementation
1. Route-coverage test (red), including whether PIN gating covers all mutating routes.
2. Migration `005-audit.js`, triggers, writer and chain verification with tests.
3. Wrap the router; add domain `record` calls to deploy, orchestration approvals and permissions first.
4. Endpoint, CLI verify and legacy importer.
5. File map update.

## 7. Tests
| Type | Scenario | Command or file |
|---|---|---|
| Unit | chain hashing, tamper detection, UPDATE/DELETE rejected | `node --test tests/audit-chain.test.js` |
| Coverage | every mutating route audited | `node --test tests/audit-route-coverage.test.js` |
| Integration | denied and failed requests recorded with outcome | `node --test tests/audit-api.test.js` |
| Redaction | no secrets or personal data in `detail` | `node --test tests/audit-redaction.test.js` |

## 8. Acceptance criteria
- [ ] 100 percent of mutating routes produce an audit row.
- [ ] `tools/audit.js verify` passes on clean data and fails after a manual row edit.
- [ ] Retention sweeps never delete audit rows.

## 9. Risks
- **Compatibility:** latency on hot paths (screen-state beacons); audit them as sampled `screen.update` only if measured cost is too high, and document the exception.
- **Security:** hash chain detects but does not prevent tampering by someone with file access; periodic signed export is a later option.
- **Rollback:** mode `off`; table remains.
