# EP-17.01: Database foundation

## 1. Identification
- **Epic:** [EP-17](README.md)
- **Priority:** P0
- **Dependencies:** none
- **Blocks:** every other EP-17 story

## 2. Context
Only `events.sqlite` exists (`ui/server/services/events/event-store.js:16,69`, `event-migrations.js`). There is no shared connection module, no migration runner for general tables and no `data/` directory. See [ADR-012](../../03-decisions/ADR-012-sqlite-sistema-de-registro.md).

## 3. Objective
A single, tested persistence layer that every later story plugs into, with safe defaults and migrations.

## 4. Requirements
**Functional**
- RF1: `ui/server/db/connection.js` opens `data/harness.sqlite` (override `HARNESS_DB_PATH`) with WAL, `busy_timeout=5000`, `foreign_keys=ON`.
- RF2: `ui/server/db/migrate.js` applies numbered, forward-only migrations from `ui/server/db/migrations/NNN-name.js` inside `BEGIN IMMEDIATE`, recorded by name in a `schema_migrations` table (`PRAGMA user_version` mirrors the highest applied number). Gaps are allowed: stories built in parallel worktrees reserve fixed numbers (see the epic README) and a lower number merged later is still applied. Refuses to run when the database holds a migration this code does not know.
- RF3: `ui/server/db/repo-base.js` offers `transaction(fn)`, prepared statement cache and JSON column helpers. Repositories live in `ui/server/db/repos/`.
- RF4: a fixture helper creates an in-memory or temp database for tests (extends 14.01 fixtures).
- RF5: `tools/lib/db-client.js` lets CLIs open the same database (same pragmas, same migration check) without the server.
- RF6: `data/` is added to `.gitignore`; `GET /api/db/health` returns schema version, size and WAL status.

**Non functional**
- 250 to 300 lines per file; connection, migration and repo helpers separate.
- Short transactions only; no network or model call inside a transaction.
- Node floor pinned in `package.json` `engines`; a smoke test fails clearly if `node:sqlite` is missing.

## 5. Architecture
Services receive repositories by injection; nothing outside `ui/server/db/` imports `node:sqlite`, except existing read-only readers of `opencode.db` and `state_5.sqlite`. Single-writer discipline: all writes go through the one connection.

## 6. Implementation
1. Add connection module and health test.
2. Add migration runner with `001-init.js` (meta table only) and tests for forward-only and newer-schema refusal.
3. Add repo base and fixtures helper.
4. Add `/api/db/health` and `.gitignore` entry.
5. Update the file map.

## 7. Tests
| Type | Scenario | Command or file |
|---|---|---|
| Unit | pragma settings applied | `node --test tests/db-connection.test.js` |
| Unit | migrations idempotent, refuse newer schema | `node --test tests/db-migrate.test.js` |
| Integration | health endpoint | `node --test tests/db-health.test.js` |

## 8. Acceptance criteria
- [ ] Fresh checkout creates `data/harness.sqlite` at schema version 1.
- [ ] Re-running migrations changes nothing.
- [ ] No source file exceeds 300 lines; `npm test` is green.

## 9. Risks
- **Compatibility:** `node:sqlite` API changes; pinned Node and smoke test.
- **Security:** database file permissions; created with user-only access where the OS allows.
- **Rollback:** the module is additive; removing the health route and `data/` reverts it.
