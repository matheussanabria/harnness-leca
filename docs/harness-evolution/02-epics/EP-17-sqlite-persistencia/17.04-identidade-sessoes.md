# EP-17.04: Local identity and server sessions

## 1. Identification
- **Epic:** [EP-17](README.md)
- **Priority:** P0
- **Dependencies:** 17.01
- **Blocks:** 17.06

## 2. Context
One shared PIN protects remote access only (`ui/server/config.js:13`, `tools/lib/network-access.js:71-75`, cookie `harness_pin` in `router.js:225`, localStorage in `app.js:80`). No users exist, so every `actor` is self-asserted. See [ADR-013](../../03-decisions/ADR-013-identidade-rbac-auditoria.md).

## 3. Objective
Every request has an authenticated identity (or an explicit `anonymous-loopback` identity), enabling audit and RBAC.

## 4. Requirements
**Functional**
- RF1: tables `users` (id, handle UNIQUE, display_name, password_hash, status, created_at), `auth_sessions` (id hash, user_id, created_at, expires_at, last_seen_at, ip, user_agent), `user_preferences` (user_id, key, value; includes active project).
- RF2: password hashing with `crypto.scrypt` and per-user salt; constant-time compare; login rate limit with lockout backoff.
- RF3: server-side sessions in an `HttpOnly`, `SameSite=Lax`, `Secure` (when HTTPS) cookie; only a hash of the token is stored; logout and expiry revoke.
- RF4: loopback bootstrap creates the first user with role `owner` (role assignment completes in 17.06); remote access requires login.
- RF5: request context middleware exposes `ctx.actor` to services; legacy PIN still accepted behind `HARNESS_LEGACY_PIN=1` and mapped to `legacy-pin` actor.
- RF6: endpoints `POST /api/auth/login|logout`, `GET /api/auth/me`, user admin endpoints (create, disable, reset password).

**Non functional**
- Threat model document in `docs/harness-evolution/04-test-plans/` before merge (session fixation, brute force, CSRF, cookie theft over LAN).
- No secrets in logs; files under 300 lines.

## 5. Architecture
`ui/server/auth/` (hash, sessions, middleware) and `ui/server/db/repos/user.repo.js`. CSRF protection via same-origin check plus a per-session token header on mutating requests.

## 6. Implementation
1. Migration `004-identity.js`, hashing module and tests.
2. Session store and middleware; wire `ctx.actor` without enforcing anything yet.
3. Login UI view with FontAwesome icons; loopback bootstrap flow.
4. Flag-gated removal path for the shared PIN.
5. Threat model and file map update.

## 7. Tests

## 8. Acceptance criteria
- [ ] Remote request without a session gets 401; loopback owner bootstrap works once.
- [ ] Only token hashes are in the database.
- [ ] With the flag off, the shared PIN no longer authenticates anything.

## 9. Risks
- **Compatibility:** mobile remote-control flow that uses the PIN; keep the flag until the login view is verified on the phone.
- **Security:** brute force over LAN; rate limit and lockout, optional TOTP later.
- **Rollback:** `HARNESS_LEGACY_PIN=1` restores the old behavior.
