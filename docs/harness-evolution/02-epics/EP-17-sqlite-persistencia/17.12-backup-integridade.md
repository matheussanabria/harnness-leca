# EP-17.12: Backup, restore and integrity checks

## 1. Identification
- **Epic:** [EP-17](README.md)
- **Priority:** P1
- **Dependencies:** 17.01
- **Blocks:** 17.13

## 2. Context
Concentrating state in one file makes backup and corruption detection mandatory. Today files are recoverable individually; a corrupt database would take everything. There is no `data/` directory or backup convention yet.

## 3. Objective
A routine, verified backup and a documented restore, so the single file is safer than the files it replaces.

## 4. Requirements
**Functional**
- RF1: `node tools/db.js backup` runs `VACUUM INTO data/backups/harness-<timestamp>.sqlite`, then `PRAGMA integrity_check` and `foreign_key_check` on the copy.
- RF2: retention of backups (daily 7, weekly 4) with a dry-run; pruning backups needs explicit confirmation outside the scheduled run.
- RF3: `node tools/db.js restore <file>` validates the copy, stops writes, keeps the replaced file as `.pre-restore`, and is audited.
- RF4: scheduled backup through the existing routines mechanism; failures raise an attention item in the Central.
- RF5: `GET /api/db/health` extends with last backup age and last integrity result; `audit verify` result included.
- RF6: `node tools/db.js export <store>` dumps any table group to JSON for inspection.

**Non functional**
- Backup must not block writers for more than a short window (WAL snapshot); files under 300 lines.

## 5. Architecture
`tools/db.js` (CLI), `tools/lib/db-backup.js`, a routine definition `db-backup`.

## 6. Implementation
1. Backup and verification with tests on a temp database.
2. Restore flow with pre-restore copy.
3. Routine and Central attention hook.
4. Runbook in `docs/` and file map update.

## 7. Tests
| Type | Scenario | Command or file |
|---|---|---|
| Unit | backup copy passes integrity check | `node --test tests/db-backup.test.js` |
| Unit | restore refuses a corrupt file | `node --test tests/db-restore.test.js` |
| Integration | failed backup creates attention item | `node --test tests/db-backup-routine.test.js` |

## 8. Acceptance criteria
- [ ] A backup restores to a database with identical row counts.
- [ ] A truncated file is rejected by restore.
- [ ] Health endpoint shows last backup time.

## 9. Risks
- **Compatibility:** Windows file locks during restore; require the server stopped or use a controlled swap.
- **Security:** backups contain all data; stored under `data/`, git-ignored; encryption at rest is a follow-up decision.
- **Rollback:** restore the `.pre-restore` file.
