# EP-17.02: Chat sessions and messages in the database

## 1. Identification
- **Epic:** [EP-17](README.md)
- **Priority:** P0
- **Dependencies:** 17.01
- **Blocks:** 17.11

## 2. Context
The engine session id is held in `localStorage` key `harness:engine-sessions:v1` (`ui/public/js/modules/chat-session-store.js:8,43`); the draft in `harness_active_chat_<slug>` (`ui/public/js/shared/state.js:181-211`); transcripts are saved as markdown by `chat-persist.js`. On 2026-11-01 Ctrl+F5 created a second OpenCode session four minutes after the first (`ses_e6811a9c...` and `ses_e68057437...`, both titled "Quero criar um prompt para detalhar um prd usando"). Existing test: `tests/chat-session-persistence.test.js`.

## 3. Objective
After any refresh, hard refresh or browser change, the user resumes the same conversation and the same engine session with full history.

## 4. Requirements
**Functional**
- RF1: tables `chat_conversations` (id, project_id, title, presentation, created_at, updated_at, archived_at), `chat_engine_sessions` (conversation_id, engine, engine_session_id, status, updated_at; PK conversation_id+engine) and `chat_messages` (id, conversation_id, seq, role, engine, content, thinking, tool_events JSON, created_at; UNIQUE conversation_id+seq).
- RF2: endpoints `GET/POST /api/chat/conversations`, `GET /api/chat/conversations/:id` (messages paged by `seq`), `PATCH` for title/archive. The server, not the browser, resolves the engine session for a conversation.
- RF3: the send path appends user and assistant messages in one transaction, assigning `seq` server-side; streaming writes the assistant message incrementally and finalizes it on completion or cancel.
- RF4: the client stores only the active conversation id (per project) and renders from the API; `chat-session-store.js` becomes a cache with server reconciliation.
- RF5: one-time idempotent importer from `projects/*/chats/*.md` and the existing `localStorage` map (via a client migration call), keyed by the `sessao` frontmatter field.
- RF6: content is redacted on write using the existing redaction rules.
- RF7: flag `HARNESS_CHAT_STORE=file|db` allows rollback; default `db` after acceptance.

**Non functional**
- Reproduce the incident first as a failing test (hard refresh with cleared storage must resume), then fix.
- Split server and client files under 300 lines.

## 5. Architecture
`ui/server/db/repos/chat.repo.js` plus `ui/server/services/chat/conversation.service.js`; controller routes under `ui/server/routes/chat.routes.js`. Client: `chat-conversation-api.js` (network), `chat-session-store.js` (cache), render modules unchanged.

## 9. Risks
- **Compatibility:** engines that cannot resume a session; record `status=expired` and start a new session with a visible notice.
- **Security:** personal data in content; redaction on write and no content in logs.
- **Rollback:** `HARNESS_CHAT_STORE=file`; markdown files are untouched by the importer.

## 10. Evidence
Branch `feat/ep-17.02-chat-store` (2026-11-20).

- **Root cause:** the engine session lived only in the browser (`localStorage`), and `resumeExistingChat` used the single `sessao` of the .md file. Cleared storage or another browser lost every other engine's session, and the quiet restore picked the newest file name, not the conversation with the latest activity.
- **Server is the source of truth:** migration `002-chat.js` (`chat_conversations`, `chat_engine_sessions`, `chat_messages`). A conversation is linked to its .md file by `source_file` (column added to RF1, unique per project). `POST /api/chat/save` mirrors into the database in one transaction and appends only the turns not stored yet; `seq` is assigned by the server.
- **API:** `GET/POST /api/chat/conversations` (`?project=&file=` returns one conversation with its sessions), `GET/PATCH /api/chat/conversations/:id` (messages paged by `seq`), `POST /api/chat/conversations/sessions` and `POST /api/chat/conversations/import-sessions`. The sessions route is POST, not PUT: `ui/server.js` refuses PUT outside `/api/canvas/`.
- **Client:** `chat-session-store.js` is a cache. A new session of a saved chat goes to the server; `reconcileEngineSessions` lets the server win when a chat is opened or restored; `migrateLocalSessionsOnce` imports the old map once per project. The quiet restore asks the server for the conversation with the latest activity, with the newest file as fallback.
- **Redaction:** content goes through `tools/lib/redact.js` before it is stored, on save and on import (tested with a fake key).
- **Importer:** `node tools/migrate/chat-import.js [--project] [--dry-run]`. Trial on a copy of the database with the real `projects/`: 1722 conversations, 16538 messages and 1722 sessions in 17 s; the second run skipped all 1722.
- **Rollback:** `HARNESS_CHAT_STORE=file` (routes answer 503, save still writes the .md, the browser falls back to its cache). Default is the database.
- **Tests:** `chat-repo` (6), `chat-conversation-api` (7), `chat-import-md` (3), `chat-session-server` (5, the F5 regression) pass; full suite 2826 pass after fixing `chat-mobile-interaction`, which inlines the session store.
- **Divergences:** RF3 streaming is not written message by message: the run journal (EP-23.02) already keeps the streaming answer durable, and the message is stored when the turn ends (auto save). RF4 is partial: the screen still renders from the .md and the local cache; the server resolves sessions and the conversation to restore. The importer is a second writer of the chat tables (`owners.js`: web and cli), only for files not linked yet. Merge or link of two conversations in the UI is not built.
- **Acceptance:** Aceita em 2026-11-23 por decisão do usuário: o Harness ainda não existe na VPS, então as conferências que dependem dela ou do navegador ficam como pendências.
- **Pending:** manual check in the browser (clear site data, reload, send a message: same engine session); run the importer on the real database after the merge.
