# EP-17.02: Chat sessions and messages in the database

## 1. Identification
- **Epic:** [EP-17](README.md)
- **Priority:** P0
- **Dependencies:** 17.01
- **Blocks:** 17.11

## 2. Context
The engine session id is held in `localStorage` key `harness:engine-sessions:v1` (`ui/public/js/modules/chat-session-store.js:8,43`); the draft in `harness_active_chat_<slug>` (`ui/public/js/shared/state.js:181-211`); transcripts are saved as markdown by `chat-persist.js`. On 2026-11-01 Ctrl+F5 created a second OpenCode session four minutes after the first (`ses_e6811a9c...` and `ses_e68057437...`, both titled "Quero criar um prompt para detalhar um prd usando"). Existing test: `tests/chat-session-persistence.test.js`.

## 3. Objective
After any refresh, hard refresh or browser change, the user resumes the same conversation and the same engine session with full history.

## 4. Requirements
**Functional**
- RF1: tables `chat_conversations` (id, project_id, title, presentation, created_at, updated_at, archived_at), `chat_engine_sessions` (conversation_id, engine, engine_session_id, status, updated_at; PK conversation_id+engine) and `chat_messages` (id, conversation_id, seq, role, engine, content, thinking, tool_events JSON, created_at; UNIQUE conversation_id+seq).
- RF2: endpoints `GET/POST /api/chat/conversations`, `GET /api/chat/conversations/:id` (messages paged by `seq`), `PATCH` for title/archive. The server, not the browser, resolves the engine session for a conversation.
- RF3: the send path appends user and assistant messages in one transaction, assigning `seq` server-side; streaming writes the assistant message incrementally and finalizes it on completion or cancel.
- RF4: the client stores only the active conversation id (per project) and renders from the API; `chat-session-store.js` becomes a cache with server reconciliation.
- RF5: one-time idempotent importer from `projects/*/chats/*.md` and the existing `localStorage` map (via a client migration call), keyed by the `sessao` frontmatter field.
- RF6: content is redacted on write using the existing redaction rules.
- RF7: flag `HARNESS_CHAT_STORE=file|db` allows rollback; default `db` after acceptance.

**Non functional**
- Reproduce the incident first as a failing test (hard refresh with cleared storage must resume), then fix.
- Split server and client files under 300 lines.

## 5. Architecture
`ui/server/db/repos/chat.repo.js` plus `ui/server/services/chat/conversation.service.js`; controller routes under `ui/server/routes/chat.routes.js`. Client: `chat-conversation-api.js` (network), `chat-session-store.js` (cache), render modules unchanged.

## 6. Implementation
1. Write the failing F5 test and confirm the root cause (read `resumeExistingChat` in `chat-persist.js`).
2. Migration `002-chat.js` and repository with tests.
3. Conversation service and endpoints; keep legacy `/api/chat/save` working.
4. Client switch to server-resolved sessions; remove reliance on `localStorage` for ids.
5. Importer and rollback flag; run importer on a copy of `projects/` first.
6. Update the file map.

## 8. Acceptance criteria
- [ ] Ctrl+F5 never creates a new engine session for an existing conversation.
- [ ] History survives server restart and a different browser profile.
- [ ] Both 2026-11-01 PRD chats import without duplicates and can be merged or linked by the user.
- [ ] Golden-master tests for chat format still pass.

## 9. Risks
- **Compatibility:** engines that cannot resume a session; record `status=expired` and start a new session with a visible notice.
- **Security:** personal data in content; redaction on write and no content in logs.
- **Rollback:** `HARNESS_CHAT_STORE=file`; markdown files are untouched by the importer.
