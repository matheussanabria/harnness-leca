# EP-17.03: Screen state and history in the database

## 1. Identification
- **Epic:** [EP-17](README.md)
- **Priority:** P0
- **Dependencies:** 17.01
- **Blocks:** 17.08

## 2. Context
EP-14 stores one JSON file per screen and project plus a 500-action history ring (`ui/server/services/screen-state/store.js:74-75,125-133`), with `rev` optimistic concurrency and a 64 KB cap. EP-14 explicitly allows replacing the file store with SQLite without changing the HTTP contract. Browser fallback keys: `leca.screen-state.v1:*` (`ui/public/js/shared/screen-state.js:8,37`).

## 3. Objective
Same endpoints and behavior, backed by transactional storage, with history queries and no file-per-screen sprawl.

## 4. Requirements
**Functional**
- RF1: tables `screen_state` (project_id, screen_id, scope, state JSON, rev, updated_at; PK project_id+scope+screen_id) and `screen_history` (id, project_id, screen_id, at, action JSON) with a trigger or service-level ring of 500 per screen.
- RF2: `rev` compare-and-set inside one transaction; conflict returns the current state as today.
- RF3: swap implementation inside `screen-state/store.js` behind the existing interface; routes in `screens.routes.js:14-17` unchanged.
- RF4: idempotent importer from `projects/*/ui-state/*.json` and `.history.jsonl`; `global/ui-state/` imported as `scope=global`.
- RF5: `localStorage` remains an offline cache only; the server value wins on load when `rev` is newer.

**Non functional**
- Keep the 64 KB state cap. Files under 300 lines.

## 5. Architecture
`ui/server/db/repos/screen-state.repo.js` implements the store interface already defined in 14.04/14.05. No client contract change.

## 6. Implementation
1. Migration `003-screen-state.js` and repository tests (CAS, ring, size cap).
2. Switch the store implementation behind a flag `HARNESS_SCREEN_STORE=file|db`.
3. Importer; run against a copy of `projects/` and compare counts.
4. Update the file map.

## 7. Tests
| Type | Scenario | Command or file |
|---|---|---|
| Contract | existing screen-state tests pass unchanged on the DB store | `node --test tests/screen-state*.test.js` |
| Concurrency | two writers with stale `rev` | `node --test tests/screen-state-repo.test.js` |
| Importer | idempotent import, ring trimmed to 500 | `node --test tests/screen-state-import.test.js` |

## 8. Acceptance criteria
- [ ] All 13 screens behave identically on `db` and `file`.
- [ ] `ui-state/` files are no longer written when the flag is `db`.
- [ ] F5 on every screen restores state.

## 9. Risks
- **Compatibility:** beacon writes on unload (`POST state`) must stay fast; synchronous prepared statements keep them under a few milliseconds.
- **Security:** state may contain draft text; same redaction scope as chat when it holds message drafts.
- **Rollback:** flag back to `file`; old files are never deleted by this story.
