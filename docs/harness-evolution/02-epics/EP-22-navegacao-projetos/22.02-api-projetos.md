# EP-22.02: API de projetos

## 1. Identificação
- **Épico:** [EP-22](README.md)
- **Prioridade:** P1
- **Dependências:** 22.01
- **Bloqueia:** 22.04 (categoria e fixados no seletor), 22.05, 22.06
- **Pode tocar além da lista acima:** o agregador de rotas (`ui/server/routes`, só acrescentar o grupo novo) e `ui/server/controllers/overview.controller.js` apenas se for preciso extrair o cache de estatísticas.

## 2. Contexto
O cliente não tem uma lista única e leve de projetos com classificação. Montar essa lista chamando o resumo de cada projeto custaria um `scan` por projeto; a Visão geral evita isso com um cache por fingerprint de arquivos (`overviewCached`).

## 3. Objetivo
Uma chamada devolve todos os projetos com o necessário para listar e filtrar, e outra grava a classificação de um projeto.

## 4. Requisitos
**Funcionais**
- RF1. `GET /api/projects` devolve, por projeto: `slug`, `category` (id ou `null`), `tags`, `pinned`, `archived`, `chatCount`, `lastChatAt`, `pendingReviews`, `invalid` (booleano) e, no envelope, `taxonomy` e `invalidCount`.
- RF2. A lista inclui arquivados; quem consome filtra (RN3). Projeto com `project.json` inválido aparece com os padrões e `invalid: true`; a lista nunca falha por causa de um projeto.
- RF3. `POST /api/project/:slug/meta` aceita `{ category?, tags?, pinned?, archived? }`, grava por mesclagem (22.01) e devolve o registro atualizado.
- RF4. A escrita só vale em loopback: fora dele, HTTP 403. `slug` desconhecido: 404. Corpo inválido: 400 com o campo e o motivo.
- RF5. A leitura segue a mesma regra de PIN das demais rotas `/api/`.

**Não funcionais**
- Desempenho: com 100 projetos, a resposta sai de um único percurso; `chatCount`, `lastChatAt` e `pendingReviews` vêm do cache de estatísticas existente, sem novo `scan` por requisição.
- Controller e rotas em arquivos separados, para manter o agregador pequeno; cada arquivo abaixo de 300 linhas.
- Erros no formato estruturado já usado pelos outros controllers (`code`, mensagem).

**Fora de escopo**
- Interface, atalho e filtros (22.03 em diante). Renomear ou mover pastas de projeto.

## 5. Arquitetura
- `GET /api/projects` combina `listMeta` (22.01) com as estatísticas do cache da Visão geral. Decisão a registrar: reaproveitar o cache existente por chamada direta ao serviço, sem duplicá-lo.
- Contrato de resposta:
```json
{ "projects": [{ "slug": "meu-gtd", "category": "pessoal", "tags": ["gtd"], "pinned": false, "archived": false,
                 "chatCount": 14, "lastChatAt": "2026-11-12T10:00:00Z", "pendingReviews": 2, "invalid": false }],
  "taxonomy": [{ "id": "pessoal", "label": "Pessoal", "icon": "fa-user" }], "invalidCount": 0 }
```

## 6. Implementação
1. Extrair, se necessário, a função de estatísticas do cache para uso fora do controller da Visão geral, sem mudar o comportamento dela.
2. Criar o controller com os dois handlers e a validação de corpo.
3. Criar `project-meta.routes.js` e registrar o grupo no agregador de rotas.
4. Conferir que um teste de rotas existente (`tests/server.test.js`) continua verde.
5. Atualizar o mapa (`docs/mapa/backend/projects/project-meta.md`) e rodar `node tools/mapa.js build --write`.

## 8. Critérios de aceite
- [ ] `GET /api/projects` lista os 25 projetos reais com os campos do contrato.
- [ ] Nenhuma requisição dispara `scan` novo por projeto além do cache existente.
- [ ] A escrita é recusada fora do loopback e para slug inexistente.
- [ ] Testes focados, regressão de rotas e `npm run check` passam; mapa atualizado.

## 9. Riscos
- **Compatibilidade:** extrair o cache pode alterar a Visão geral; a regressão de `overview.test.js` cobre.
- **Segurança:** é a primeira rota de escrita de metadados; o teste de loopback é obrigatório.
- **Rollback:** remover o grupo de rotas do agregador.
