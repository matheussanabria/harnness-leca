# EP-22.01: Metadados do projeto e taxonomia de categorias

## 1. Identificação
- **Épico:** [EP-22](README.md)
- **Prioridade:** P1
- **Dependências:** nenhuma
- **Bloqueia:** 22.02

## 2. Contexto
Os projetos são pastas em `projects/<slug>/` (25 hoje) sem nenhum metadado de classificação. Não há onde guardar categoria, tags, fixado ou arquivado, e nada impede variações de grafia se cada tela criar a sua lista.

## 3. Objetivo
**Como** Matheus, **quero** que cada projeto tenha uma categoria e tags guardadas no próprio projeto, **para que** seletor e aba Projetos filtrem sempre pelos mesmos dados.

## 4. Requisitos
**Funcionais**
- RF1. Contrato `projects/<slug>/project.json`: `{ "schema": 1, "category": "<id>|null", "tags": ["..."], "pinned": false, "archived": false, "updatedAt": "<ISO>" }`.
- RF2. Taxonomia global em `global/project-taxonomy.json`: `{ "schema": 1, "categories": [{ "id", "label", "icon" }] }` com as quatro categorias iniciais: `trabalho` (Trabalho), `negocios` (Negócios), `pessoal` (Pessoal), `plataforma-ia` (Plataforma e IA). Categoria `null` é exibida como "Sem categoria" e não faz parte do arquivo.
- RF3. Leitura tolerante: `project.json` ausente devolve os padrões; JSON inválido ou categoria fora da taxonomia devolve os padrões com `invalid: true` e o motivo, sem lançar erro.
- RF4. Gravação por mesclagem: só os campos enviados mudam; escrita atômica; `updatedAt` definido pelo servidor.
- RF5. Normalização de tags: minúsculas, sem espaços nas pontas, até 24 caracteres, no máximo 8, sem duplicata, ordem preservada. Valor inválido é rejeitado com erro estruturado (`code`, campo), nunca truncado em silêncio.
- RF6. `slug` validado contra a lista real de projetos antes de qualquer leitura ou escrita (sem `..`, sem separador).

**Não funcionais**
- Serviço e normalização separados: a normalização é pura, sem I/O, para ser reaproveitada nos testes e, se preciso, no cliente.
- Escrita atômica no mesmo padrão já usado em `projects/.active`. Se `projects/<slug>/` for ignorado pelo git, registrar a decisão sobre versionar o `project.json` nas notas do épico.
- Arquivos abaixo de 300 linhas, sem emojis.

**Fora de escopo**
- Endpoints HTTP (22.02) e qualquer interface.
- Sugestão automática de categoria por LLM.

## 5. Arquitetura
- `project-meta-normalize.js`: `normalizeTag`, `normalizeTags`, `validateMeta(meta, taxonomy)`, `defaultMeta()`; funções puras.
- `project-meta.service.js`: `readTaxonomy()`, `readMeta(slug)`, `writeMeta(slug, patch)`, `listMeta(slugs)`.
- Os ids de categoria são estáveis (`plataforma-ia`); o rótulo e o ícone podem mudar sem migrar dados. O mockup usa chaves curtas (`trab`, `neg`, `pes`, `plat`, `sem`) só como classes de CSS.

## 6. Implementação
1. Criar `global/project-taxonomy.json` com as quatro categorias.
2. Criar o módulo de normalização e validação, com os testes primeiro.
3. Criar o serviço de leitura tolerante e de gravação atômica.
4. Acrescentar a linha no mapa (`docs/mapa/backend/projects/project-meta.md`) e rodar `node tools/mapa.js build --write`.

## 7. Testes
| Tipo | Cenário | Comando ou arquivo |
|---|---|---|
| Unitário | Tags: caixa, espaços, 24 caracteres, limite de 8, duplicata, ordem | `node --test tests/project-meta.test.js` |
| Unitário | Categoria fora da taxonomia rejeitada; `null` aceito | `tests/project-meta.test.js` |
| Integração | `project.json` ausente, vazio, JSON inválido e campo com tipo errado devolvem padrões sem lançar | `tests/project-meta.test.js` |
| Integração | Gravação por mesclagem preserva campos não enviados; arquivo nunca fica pela metade | `tests/project-meta.test.js` |
| Segurança | Slug com `..`, barra e slug inexistente | `tests/project-meta.test.js` |

Usar o fixture de projeto temporário (`tests/helpers/project-fixture.js`); nenhum teste toca `projects/` real.

## 8. Critérios de aceite
- [ ] Os padrões saem corretos para os 25 projetos atuais (nenhum tem `project.json`).
- [ ] `project.json` inválido não lança erro e é sinalizado em `invalid`.
- [ ] Tag inválida é rejeitada com erro estruturado, nunca alterada em silêncio.
- [ ] Slug fora da lista real é rejeitado antes de tocar o disco.
- [ ] `node --test tests/project-meta.test.js` e `npm run check` passam; mapa atualizado.

## 9. Riscos
- **Compatibilidade:** `project.json` novo em pasta de projeto; confirmar que nenhum scanner (`sync`, `export-context`, inventário) trata arquivos desconhecidos na raiz do projeto como erro.
- **Segurança:** caminho montado só a partir de slug validado.
- **Rollback:** apagar o serviço e os `project.json`; nenhuma tela depende dele nesta história.
