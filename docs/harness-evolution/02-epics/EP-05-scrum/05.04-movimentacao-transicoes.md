# EP-05.04: Movimentação de histórias e transições

## 1. Identificação
- **Épico:** [EP-05](README.md)
- **Prioridade:** P1
- **Dependências:** EP-05.02 e EP-05.03
- **Bloqueia:** 05.05 e 05.06

## 2. Contexto
As histórias já são projetadas por `laneId`, mas a operação legada altera somente quatro status e não registra histórico. A movimentação precisa respeitar o workflow canônico mesmo quando a ordem visual das raias for personalizada.

## 3. Objetivo
Permitir mover histórias entre etapas adjacentes por arraste ou botões acessíveis, validando a transição no backend e persistindo uma trilha atômica sem perder a origem Jira ou o status legado.

## 4. Requisitos
**Funcionais**
- RF1. Validar transições pela sequência canônica dos 12 IDs, independente da ordem visual configurada.
- RF2. Permitir somente avanço ou retorno para etapa adjacente; rejeitar salto, no-op e raia desconhecida.
- RF3. Impedir qualquer transição com raia de origem ou destino inativa.
- RF4. Exigir `expectedLaneId` para detectar cartões movidos por outra sessão.
- RF5. Atualizar `laneId` e o status legado compatível no mesmo comando.
- RF6. Acrescentar histórico com história, origem, destino, status, instante e origem do dado.
- RF7. Preservar identidade, conteúdo, Sprint, épico, snapshot Jira e configuração das raias.
- RF8. Drag-and-drop e botões anterior/próxima devem usar o mesmo endpoint.

**Não funcionais**
- Persistência atômica no schema v2 e testes somente em diretórios temporários.
- Alternativa por teclado, foco restaurado e mudança anunciada por `aria-live`.
- Ícones exclusivamente FontAwesome e arquivos de código abaixo de 300 linhas.
- Impedimentos, filtros e métricas permanecem na EP-05.05.

## 5. Contrato
- `POST /api/project/:slug/scrum/story/transition`
- Request: `{ storyId, fromLaneId, toLaneId }`.
- Sucesso: Scrum atualizado com `transitionHistory` e transições permitidas por história.
- Conflito de origem: HTTP 409 sem gravação.
- Regra inválida, raia inativa ou payload inválido: HTTP 400 sem gravação.

## 6. Testes
| Tipo | Cenário | Arquivo |
|---|---|---|
| Unidade | Matriz adjacente, status legado e raias inativas | `tests/project-scrum-transitions.test.js` |
| Integração | Persistência/histórico, conflito e origem Jira | `tests/project-scrum-transitions.test.js` |
| UI / acessibilidade | Drag, botões, endpoint único, foco e anúncio | `tests/design-scrum-transitions.test.js` |
| Regressão | Migração, configuração e ordem das raias | testes focados do Scrum |

## 7. Critérios de aceite
- [x] Avanço e retorno adjacentes são persistidos com histórico.
- [x] Saltos, no-op, IDs desconhecidos e raias inativas são rejeitados sem alterar o arquivo.
- [x] Origem divergente retorna conflito HTTP 409 sem sobrescrita.
- [x] `laneId` e `status` legado permanecem coerentes nas 12 etapas.
- [x] Reordenar visualmente as raias não altera a matriz de transições.
- [x] Histórias Jira preservam identidade e proveniência; somente o estado local é gravado.
- [x] Drag-and-drop e botões anterior/próxima usam o mesmo endpoint.
- [x] Operação por teclado possui nome acessível, foco visível e feedback anunciado.
- [x] Nenhum `scrum.json` real é alterado pelos testes.

## 8. Riscos
- **Concorrência:** mitigada exigindo a raia de origem conhecida pelo cliente.
- **Compatibilidade:** grupos de raias são projetados nos quatro status legados; o `laneId` continua sendo a classificação precisa.
- **Workflow:** a matriz usa a ordem canônica, não `order`, para que personalização visual não mude regras.

## 9. Evidências
- 33/33 testes focados das EP-05.01 a EP-05.04 aprovados.
- Suíte integral no estado compartilhado final: 544/544 testes aprovados.
- `npm run check`: 492 JavaScript e 10 JSON sem erros.
- `npm run types`: baseline global permanece vermelho, sem erros nos módulos Scrum alterados.
- Todos os ensaios de persistência usaram diretórios temporários; nenhum `projects/*/scrum.json` foi alterado.
