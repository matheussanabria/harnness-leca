# EP-05.03: Reordenação horizontal persistida por projeto

## 1. Identificação
- **Épico:** [EP-05](README.md)
- **Prioridade:** P1
- **Dependências:** EP-05.02
- **Bloqueia:** 05.05 e 05.06

## 2. Contexto
As doze raias já possuem IDs estáveis e campo `order`, mas a ordem ainda é canônica e não pode ser personalizada. O quadro precisa persistir uma permutação por projeto sem confundir a posição visual com o status legado ou a classificação `laneId` das histórias.

## 3. Objetivo
Permitir que o usuário reorganize horizontalmente as raias visíveis por arraste ou por botões acessíveis, salvando a ordem no `scrum.json` do projeto e prevenindo sobrescrita concorrente.

## 4. Requisitos
**Funcionais**
- RF1. Aceitar somente uma permutação completa dos 12 IDs canônicos.
- RF2. Persistir `order` contíguo de 0 a 11 por projeto, mantendo `schemaVersion: 2`.
- RF3. Reordenar por drag-and-drop ou botões mover à esquerda/direita, usando o mesmo comando HTTP.
- RF4. Manter raias ocultas em suas posições ao reordenar somente as raias visíveis.
- RF5. Preservar integralmente histórias, `status`, `laneId`, sprints e épicos.
- RF6. Usar revisão otimista e responder conflito quando outra sessão já tiver alterado as raias.
- RF7. Alterações posteriores de nome, descrição, cor, visibilidade ou ativação preservam a ordem.

**Não funcionais**
- Escrita atômica e testes restritos a diretórios temporários.
- Alternativa operável por teclado para toda interação de arraste.
- Feedback anunciado, foco restaurado e ícones exclusivamente FontAwesome.
- Nenhum arquivo de código acima de 300 linhas.

## 5. Arquitetura
- O domínio valida a permutação e produz as raias com `order` normalizado.
- `lanesRevision` implementa concorrência otimista para configuração e ordenação.
- `POST /api/project/:slug/scrum/lanes/order` recebe `laneIds` e `expectedRevision`.
- O modelo frontend calcula a ordem das raias visíveis sem DOM; o controlador de UI concentra rede, drag, botões, feedback e foco.

## 6. Implementação
1. Fazer a hidratação respeitar `order` persistido.
2. Adicionar comando versionado de reordenação e conflito HTTP 409.
3. Adicionar controles de arraste e botões acessíveis no cabeçalho das raias.
4. Preservar a posição de raias ocultas e a ordem ao editar atributos.
5. Cobrir domínio, persistência, concorrência e UI.

## 7. Testes
| Tipo | Cenário | Comando ou arquivo |
|---|---|---|
| Unitário | Permutação, IDs e ordem contígua | `tests/project-scrum-lane-order.test.js` |
| Integração | Persistência, revisão e conflito sem alterar histórias | `tests/project-scrum-lane-order.test.js` |
| UI / acessibilidade | Ordem visível, drag, botões, foco e anúncio | `tests/design-scrum-lane-order.test.js` |
| Regressão | Migração, fontes e configuração das raias | testes focados do Scrum |

## 8. Critérios de aceite
- [x] Uma permutação válida é persistida e reaparece após nova leitura.
- [x] IDs ausentes, duplicados ou desconhecidos são rejeitados.
- [x] Reordenar não altera `status`, `laneId` nem qualquer história.
- [x] Uma revisão obsoleta retorna conflito e não sobrescreve o arquivo.
- [x] Configurar atributos depois de reordenar mantém a ordem vigente.
- [x] Drag-and-drop e botões usam o mesmo endpoint.
- [x] A alternativa por teclado tem nome acessível, foco visível, feedback anunciado e restauração do foco.
- [x] Nenhum `scrum.json` real é alterado pelos testes.

## 9. Riscos
- **Concorrência:** mitigada por `lanesRevision` comparada antes da gravação síncrona e atômica.
- **Compatibilidade:** arquivos sem revisão são hidratados com zero; toda mutação HTTP deve enviar a revisão conhecida. Ausência ou corrupção de `order` recompõe a ordem canônica.
- **Rollback:** remover `order` e `lanesRevision` faz a hidratação retornar aos defaults sem alterar histórias.

## 10. Evidências
- Testes focados: `node --test tests/project-scrum-lane-order.test.js tests/project-scrum-lanes.test.js tests/design-scrum-lane-order.test.js`.
- Suíte integral: `npm test` com 518/518 testes aprovados.
- Qualidade: `npm run check` validou 482 arquivos JavaScript e 10 JSON sem erros.
- Tipos: o baseline global permanece com falhas conhecidas; o recorte dos módulos Scrum alterados não apresentou erro.
- Persistência testada exclusivamente em diretórios temporários; nenhum `projects/*/scrum.json` foi usado.
