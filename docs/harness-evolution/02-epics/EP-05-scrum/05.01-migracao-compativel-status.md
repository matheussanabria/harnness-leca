# EP-05.01: Migração compatível de status

## 1. Identificação
- **Épico:** [EP-05](README.md)
- **Prioridade:** P1
- **Dependências:** EP-04, EP-00.03 e EP-00.04
- **Bloqueia:** 05.02, 05.03, 05.04 e 05.05

## 2. Contexto
Os arquivos `projects/<slug>/scrum.json` não possuem versão de schema e armazenam quatro status fixos. O sanitizador também reduz qualquer valor desconhecido a `todo`. A evolução para raias configuráveis precisa preservar o leitor atual, os IDs, a Sprint e o significado dos dados existentes.

## 3. Objetivo
Introduzir o schema Scrum v2 por migração automática, idempotente, auditável e reversível, mantendo o campo `status` para consumidores antigos e adicionando `laneId` como base do novo workflow.

## 4. Requisitos
**Funcionais**
- RF1. Arquivo sem `schemaVersion` é tratado como v1 e migrado para v2 na primeira leitura.
- RF2. Preservar `status` e adicionar o mapeamento `todo → pronto-para-dev`, `in_progress → em-desenvolvimento`, `review → em-revisao`, `done → concluido`.
- RF3. Status desconhecido não pode ser descartado; permanece em `status`, recebe `laneId: null` e aparece no histórico da migração.
- RF4. Criar uma única cópia `scrum.v1.backup.json` antes da primeira gravação migrada.
- RF5. Gravar `scrum.json` por temporário e rename atômico.
- RF6. Leituras subsequentes não alteram o arquivo nem duplicam o histórico.
- RF7. Mutações de história mantêm `status` e `laneId` coerentes durante a compatibilidade.
- RF8. Disponibilizar operação interna de rollback a partir do backup versionado.

**Não funcionais**
- Não alterar o snapshot Jira nem documentos de história.
- Não materializar ainda as 12 raias; isso pertence à EP-05.02.
- Preservar o contrato HTTP atual e os quatro valores de `status` aceitos pela UI.
- Implementação modular, sem ampliar arquivos acima do limite arquitetural.

## 5. Modelo v2
```json
{
  "schemaVersion": 2,
  "migrationHistory": [{
    "id": "scrum-status-v1-to-v2",
    "fromVersion": 1,
    "toVersion": 2,
    "appliedAt": "ISO-8601",
    "mappedStories": 4,
    "unmappedStatuses": []
  }],
  "stories": [{
    "status": "in_progress",
    "laneId": "em-desenvolvimento"
  }]
}
```

## 6. Estratégia de rollback
1. Parar gravações da versão nova.
2. Exportar mudanças posteriores, se existirem.
3. Restaurar `scrum.v1.backup.json` por escrita atômica.
4. Voltar ao leitor v1 antes de reabrir o serviço.

## 7. Testes planejados
- Migração pura preserva identidade, Sprint, pontos, status e contagens.
- Os quatro status conhecidos recebem a raia proposta.
- Status desconhecido é preservado e auditado.
- Segunda migração é no-op.
- Migração em arquivo cria um backup único e não deixa temporários.
- Rollback restaura exatamente o documento v1.
- Operações de criação e movimentação mantêm o par status/raia.

## 8. Critérios de aceite
- [x] Schema v2 publicado sem remover campos legados.
- [x] Migração automática é idempotente.
- [x] Backup versionado e escrita atômica estão cobertos por teste.
- [x] Rollback está implementado e ensaiado em diretório temporário.
- [x] Nenhum status desconhecido é perdido silenciosamente.
- [x] Testes focados e `npm run check` passam.

## 9. Riscos
- **Concorrência:** esta história melhora atomicidade, mas locking multi-processo permanece para hardening posterior.
- **Rollback:** o leitor v2 remigraria um backup restaurado; o runbook exige voltar ao leitor v1 antes de reiniciar.
- **Raias:** `laneId` prepara a expansão, mas a configuração e ordenação das 12 raias pertencem à 05.02.

## 10. Evidências
- `project-scrum-migration.js` concentra versão, mapeamento, backup, escrita atômica e rollback em 122 linhas.
- Persistência e resolver expõem `schemaVersion` e `migrationHistory`; mutações mantêm `status` e `laneId` coerentes.
- `node --test tests/project-scrum-migration.test.js tests/project-scrum-sources.test.js tests/design-scrum-details.test.js`: 12/12 testes aprovados.
- `npm test`: 478/478 testes aprovados.
- Checagem de tipos focada dos quatro serviços alterados: nenhum erro.
- `npm run check`: 459 arquivos JavaScript e 10 JSON sem erro.
- Os cinco `scrum.json` reais foram apenas inventariados; os ensaios de migração e rollback ocorreram em diretórios temporários.
