# EP-04.03: Persistência de janelas, filtros e recursos selecionados

## 1. Identificação
- **Épico:** [EP-04](README.md)
- **Prioridade:** P1
- **Dependências:** EP-04.01, EP-04.02 e EP-01.08
- **Bloqueia:** 04.04 e 04.05

## 2. Contexto
O `LayoutPersistenceManager` já grava geometria e visibilidade por projeto, mas descarta o `resourceId` das janelas. Sua restauração também reutiliza IDs serializados, falhando para módulos não singleton, e não há contrato central para filtros ou seleções mantidas pelos módulos.

## 3. Objetivo
Publicar um snapshot versionado de workspace que restaure o conjunto exato de janelas e preserve, por projeto, filtros e recursos selecionados como contexto opaco para os consumidores.

## 4. Requisitos
**Funcionais**
- RF1. Persistir e restaurar o layout completo, incluindo `resourceId`, foco, minimização e apresentação.
- RF2. Restaurar janelas singleton e não singleton usando os novos IDs gerados pela store.
- RF3. Persistir filtros e recursos selecionados em mapas JSON independentes por módulo.
- RF4. Isolar snapshots por projeto e rejeitar operação sem projeto válido, versão incompatível ou conteúdo corrompido.
- RF5. Expor `save`, `restore` e `clear` em `windowManager.persistence`, usando por padrão o projeto central.
- RF6. Retornar o contexto restaurado para que cada consumidor aplique seu estado sem acoplar o Window Manager à UI.

**Não funcionais**
- Envelope com versão explícita e compatibilidade com layouts `_v: 1` existentes.
- Nenhuma alteração nos arquivos `chat*`, `office*` ou nas interfaces pertencentes à trilha Gemini.
- Novo módulo coeso abaixo de 200 linhas; arquivos existentes permanecem abaixo do teto de 300 linhas.
- Somente dados JSON serializáveis; falhas de storage não podem corromper o estado em memória.

## 5. Arquitetura
- `layout-persistence.js`: serialização e aplicação canônica do layout, incluindo remapeamento de IDs e `resourceId`.
- `workspace-persistence.js`: envelope versionado de layout, filtros e recursos por projeto.
- `window-manager.js`: fachada pública `persistence` orientada ao projeto selecionado.
- Consumidores: recebem `{ filters, resources }` no retorno de `restore` e continuam donos de suas regras de UI.

## 6. Implementação
1. Consolidar a aplicação de layouts em uma função compartilhada.
2. Preservar `resourceId` na serialização e restauração.
3. Criar o gerenciador de snapshot composto e validação defensiva.
4. Publicar a capacidade na fachada usando o seletor central.
5. Proteger isolamento, corrupção e regressões com testes.

| Regressão | Layouts nomeados e Window Manager | `node --test tests/workspace-persistence.test.js tests/layout-persistence.test.js tests/workspace-presets.test.js tests/workspace-session.test.js tests/window-manager.test.js` |

## 8. Critérios de aceite
- [x] O snapshot composto contém layout, filtros e recursos com versão explícita.
- [x] `resourceId`, foco e minimização sobrevivem à restauração.
- [x] Janelas não singleton são restauradas com IDs reais, sem referências antigas.
- [x] Snapshots não vazam entre projetos.
- [x] Payload corrompido ou incompatível é rejeitado sem resetar janelas abertas.
- [x] `windowManager.persistence` usa o projeto central e permite sobrescrita explícita.
- [x] Testes focados e `npm run check` passam.

## 9. Riscos
- **Consumidores:** filtros são opacos; cada módulo continua responsável por aplicá-los.
- **Compatibilidade:** layouts existentes continuam válidos, com `resourceId` opcional.
- **Concorrência:** nenhum arquivo visual da trilha Gemini será alterado.
