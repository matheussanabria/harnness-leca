# EP-04.04: Templates de workspace

## 1. Identificação
- **Épico:** [EP-04](README.md)
- **Prioridade:** P1
- **Dependências:** EP-04.02 e EP-04.03
- **Bloqueia:** 04.05

## 2. Contexto
Os presets `dev`, `scrum` e `ops` existem desde a EP-01.10, mas ainda não formam os quatro templates previstos no produto. Planejamento e Operações também referenciam módulos que não correspondem ao catálogo atual, e não há um template de Qualidade.

## 3. Objetivo
Disponibilizar quatro templates de sistema coerentes e protegidos — Desenvolvimento, Planejamento, Qualidade e Operações — compostos apenas por módulos registrados e carregáveis em qualquer projeto.

## 4. Requisitos
**Funcionais**
- RF1. Publicar exatamente quatro templates canônicos com chaves `development`, `planning`, `quality` e `operations`.
- RF2. Preservar os IDs legados `dev`, `scrum` e `ops`; adicionar `quality` sem quebrar consumidores existentes.
- RF3. Desenvolvimento abre Codex e Studio; Planejamento abre Scrum e Diário; Qualidade abre Revisão e Studio; Operações abre Datacenter e Orquestração.
- RF4. Todo módulo referenciado deve existir no `window-registry` e usar ícone FontAwesome.
- RF5. Templates são imutáveis, protegidos contra exclusão e aplicados ao projeto ativo pela API existente.
- RF6. Nenhum template padrão inclui Claude ou OpenCode, conforme a divisão atual Gemini + Codex.

**Não funcionais**
- Extrair o catálogo para módulo próprio abaixo de 200 linhas.
- Manter `SYSTEM_WORKSPACES` exportado por `workspace-presets.js` para retrocompatibilidade.
- Nenhuma alteração em interfaces `chat*` ou `office*` da trilha Gemini.
- Nenhum emoji novo em código ou interface.

## 5. Arquitetura
- `workspace-templates.js`: fonte única e imutável dos quatro templates.
- `workspace-presets.js`: CRUD de layouts customizados e reexportação compatível do catálogo.
- `window-registry.js`: registro da superfície de Revisão usada pelo template de Qualidade.
- `windowManager.workspaces`: API existente para listar e carregar os templates.

## 6. Implementação
1. Extrair os presets para um catálogo modular com metadado `templateKey`.
2. Corrigir composições para módulos existentes e adicionar Qualidade.
3. Registrar o módulo `review` com ícone FontAwesome.
4. Preservar exportações, IDs e proteção contra exclusão.
5. Validar todos os templates e suas composições com testes.

## 7. Testes
| Tipo | Cenário | Comando ou arquivo |
|---|---|---|
| Unitário | Catálogo, chaves, imutabilidade e módulos permitidos | `tests/workspace-templates.test.js` |
| Integração | Carregamento dos quatro templates por projeto | `tests/workspace-templates.test.js` |
| Regressão | Presets, sessão e persistência | `node --test tests/workspace-templates.test.js tests/workspace-presets.test.js tests/workspace-session.test.js tests/workspace-persistence.test.js tests/window-manager.test.js` |

## 8. Critérios de aceite
- [x] Os quatro templates canônicos são listados com nomes, descrições e ícones FontAwesome.
- [x] IDs legados continuam funcionando e `quality` é adicionado.
- [x] Todos os módulos usados estão registrados e carregam sem fallback desconhecido.
- [x] Nenhum template inclui Claude ou OpenCode.
- [x] Catálogo e templates não podem ser mutados em runtime.
- [x] Exclusão dos quatro templates é bloqueada.
- [x] Testes focados e `npm run check` passam.

## 9. Riscos
- **Compatibilidade:** IDs legados são mantidos; somente suas composições inválidas são corrigidas.
- **Interface:** a seleção visual dos templates permanece com a trilha Gemini.
- **Rollback:** `workspace-presets.js` continua sendo a fachada compatível do catálogo.

## 10. Evidências
- Arquivos alterados: `workspace-templates.js`, `workspace-presets.js`, `window-registry.js`, `workspace-templates.test.js` e `workspace-presets.test.js`.
- `node --test tests/workspace-templates.test.js tests/workspace-presets.test.js tests/workspace-session.test.js tests/workspace-persistence.test.js tests/window-manager.test.js`: 21/21 testes aprovados.
- `npm run check`: 452 arquivos JavaScript e 10 JSON sem erro.
- Checagem de tipos focada: nenhum erro nos três arquivos da implementação. O gate global permanece com dívida preexistente fora desta história.
- Capturas: não aplicável; contrato sem interface visual nova.
