# EP-23.03: Host de motores em processo separado

## 1. Identificação
- **Épico:** [EP-23](README.md)
- **Prioridade:** P0
- **Dependências:** 23.02
- **Bloqueia:** 23.05, 23.06
- **Pode tocar além da lista acima:** `ui/server/controllers/chat.controller.js`, `package.json` (script `host`), `SETUP.md`.

## 2. Contexto
Hoje [chat.controller.js](../../../../ui/server/controllers/chat.controller.js) chama `tools/lib/engines` dentro do processo web, então as CLIs morrem com ele. O OpenBot resolve isso com um host que não reinicia ao mudar código e uma interface que só exibe.

## 3. Objetivo
As CLIs dos motores rodam num processo Node de vida longa (`ui/engine-host.js`), sem watch; o servidor web repassa pedidos e streams para ele e pode reiniciar à vontade sem cortar respostas.

## 4. Requisitos
**Funcionais**
- RF1. `npm run host` sobe o host, que escuta só em loopback (porta configurável, padrão 4322) com token gerado na primeira subida e salvo em `data/engine-host.token` (fora do git).
- RF2. O host expõe: iniciar execução, attach com `from`, parar execução, listar execuções ativas, saúde (`/health` com versão e número de execuções ativas).
- RF3. O host é dono do registro de execuções e das tabelas `chat_runs` e `chat_run_events` (23.02): só ele escreve nelas, pela própria conexão do módulo `ui/server/db/`. O servidor web não guarda mais execução nem escreve nessas tabelas; lê pela API do host.
- RF3a. O host não escreve em nenhuma outra tabela; o que precisar (sessão do motor, por exemplo) lê pelo repositório e grava pedindo ao servidor web. Um teste confere que o host só prepara `INSERT`/`UPDATE`/`DELETE` em `chat_runs*`.
- RF4. O servidor web repassa `POST /api/chat`, `GET /api/chat/attach` e a parada para o host sem mudar o contrato do navegador.
- RF5. Se o host não estiver no ar, `npm run ui` o inicia como processo destacado (`detached`, `unref`) e espera `/health` por até 5 s; falhando, responde 503 com mensagem clara.
- RF6. Reiniciar o servidor web com uma resposta em andamento não interrompe a resposta; o navegador religa por `seq` e recebe o restante.

**Não funcionais**
- Latência extra de repasse abaixo de 5 ms por evento em loopback.
- Host sem `--watch` em qualquer modo; o host só reinicia por comando explícito.
- Cada arquivo abaixo de 300 linhas; o host reaproveita `tools/lib/engines` sem duplicar.

**Fora de escopo**
- Seletor de host e acesso remoto (23.06). Desktop.

## 5. Arquitetura
```
navegador ──SSE──► servidor web (reinicia à vontade) ──HTTP loopback + token──► host de motores ──► CLIs
                                                                                      └──► data/harness.sqlite (tabelas chat_runs*)
```
- Transporte: HTTP com SSE em loopback, para reaproveitar o formato `data: {seq,...}` atual.
- Sessão do motor (`--resume`) e permissões (`tools/lib/permissions`) passam a ser resolvidas no host.

## 6. Implementação
1. Extrair do controller a parte que dispara o motor para `ui/server/services/engine-host/` (roda dentro do host).
2. Criar `ui/engine-host.js` (bootstrap, rotas, token) e `engine-host-client.js` (repasse no servidor web).
3. Trocar o controller para usar o cliente; manter o modo antigo atrás de `HARNESS_ENGINE_HOST=0`.
4. Autostart do host em `npm run ui`; documentar em `SETUP.md`.
5. Linhas no mapa (`docs/mapa/backend/chat/` e `docs/mapa/tools/engines/`).

## 7. Testes

## 8. Critérios de aceite
- [x] Salvar um arquivo em `ui/server` com `ui:dev` rodando e uma resposta em andamento: a resposta termina completa na tela. (Coberto por teste com reinício do servidor web; falta a conferência manual no navegador.)
- [x] Parar pela tela continua parando o motor.
- [x] O host não aparece em nenhuma porta fora do loopback.

## 9. Riscos
- **Processos órfãos:** host que fica no ar com execução presa; mitigar com `RUN_GRACE_MS` e um comando `npm run host:stop`.
- **Dois escritores no mesmo arquivo:** WAL e `busy_timeout` da 17.01 com transações curtas; o dono por tabela evita conflito lógico.
- **Versão divergente:** servidor web novo com host antigo; `/health` devolve versão do protocolo e o cliente recusa versão incompatível com mensagem clara.
- **Rollback:** `HARNESS_ENGINE_HOST=0`.

## 10. Evidências
Branch `feat/ep-23.03-engine-host` (2026-11-20).

- **Processo separado:** `ui/engine-host.js` escuta só em `127.0.0.1` (padrão 4322) e cria o token em `data/engine-host.token` na primeira subida. Rotas: `/health` (protocolo, versão, pid, execuções ativas), `POST /runs`, `GET /runs`, `/runs/:id/attach`, `/runs/:id/stop`, `/permissions/answer` e `/shutdown`. Todas exigem o token e recusam pedido com cabeçalho de proxy (403).
- **Disparo extraído:** `run-starter.js` concentra validação, capacidade, registro, cartões de permissão, telemetria, HIA e CLI. O host e o modo antigo (`HARNESS_ENGINE_HOST=0`) usam o mesmo código.
- **Permissões:** o MCP do Claude passa a postar no host (`/api/permissions/request`, só do loopback direto, como o servidor web já fazia, porque o MCP não recebe o token). A resposta do usuário chega ao servidor web e é repassada ao host (`permissions.controller.js`).
- **Contrato do navegador inalterado:** o servidor web repassa `POST /api/chat`, o attach e a parada; o SSE é encaminhado byte a byte.
- **Autostart:** `npm run ui` e `ui:dev` sobem o host destacado (`detached` + `unref`, log em `logs/engine-host.log`) e esperam `/health` por até 5 s; falhando, 503 com mensagem. Dentro de `node --test` o autostart fica desligado, a não ser que o teste peça `HARNESS_ENGINE_HOST_AUTOSTART=1`: na primeira rodada da suíte um teste antigo subiu um host real destacado, que ficou órfão e foi encerrado.
- **Versão:** `/health` devolve `protocol: 1`; o cliente recusa protocolo diferente com mensagem para reiniciar o host.
- **Dono das tabelas:** `chat_runs` e `chat_run_events` passam a `host` em `owners.js`. Teste RF3a: o host roda com um registrador de `INSERT/UPDATE/DELETE` no `harness.sqlite` e só aparecem `chat_runs*` e `schema_migrations` (migração, que qualquer processo pode aplicar).
- **Event log do EP-09:** host e servidor web passam a gravar no mesmo `events.sqlite`; ganhou `busy_timeout = 5000`.
- **Latência (NFR):** 300 eventos a cada 5 ms; do motor ao cliente, direto no host p50 7 ms e p95 7 ms; passando pelo servidor web p50 7 ms e p95 8 ms. O repasse acrescenta cerca de 1 ms.
- **Testes:** `tests/engine-host.test.js` (6): reinício do servidor web no meio da resposta (20 trechos, `seq` contínuo e `done`), parada, token e proxy, 503, autostart e escrita só em `chat_runs*`. Os testes antigos que rodam motores falsos no próprio processo (`server`, `chat-run-telemetry`, `chat-run-registry`, `engines.misc`, `permissions`) usam `HARNESS_ENGINE_HOST=0`.
- **Fora da lista `owns`:** `chat.controller.js` (repasse), `permissions.controller.js` (resposta repassada), `chat-run-registry.service.js` (`listActiveRuns`), `event-store.js` (`busy_timeout`), `owners.js`, `ui/server.js` (autostart na subida), `package.json` (`host`, `host:stop`) e `SETUP.md`.
- **Pendente:** conferência manual no navegador (resposta longa + salvar arquivo em `ui/server` com `ui:dev`). Depois de mudar `tools/lib/engines` é preciso `npm run host:stop`: o host não recarrega código sozinho (a 23.05 trata o reinício seguro).
