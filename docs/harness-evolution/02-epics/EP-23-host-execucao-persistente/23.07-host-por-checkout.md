# EP-23.07: Host de motores por checkout

## 1. Identificação
- **Épico:** [EP-23](README.md)
- **Prioridade:** P1
- **Dependências:** 23.03 (host separado) e 23.05 (reinício seguro)
- **Bloqueia:** nada; a 23.06 (seletor de host) reaproveita a identidade do host
- **Pode tocar além da lista acima:** `SETUP.md` (seção Engine host) e `docs/mapa/backend/chat/engine-host.md`.

## 2. Contexto
O host de motores escuta numa porta fixa (4322, `DEFAULT_PORT` em `protocol.js`) em todo checkout, mas o token fica em `data/engine-host.token` de cada pasta. Um servidor de teste subido de um worktree inicia o host dele nessa porta, e a `main` passa a falar com um host que não é o dela.

Reproduzido em 2026-11-22, com um host de outra raiz numa porta de teste:
- O chat da `main` recebe "O host de motores recusou o token deste servidor. Reinicie o host (npm run host:stop)" (`ensureHost`, `engine-host-client.js`). A mensagem não diz de onde é o host que está lá.
- `npm run host:stop` rodado na `main` usa o token da `main`, leva 401 e mesmo assim imprime "stop requested; runs cut: ?", porque `stopRunningHost` (`ui/engine-host.js`) não olha o status. O host continua vivo e a instrução do erro não resolve nada.
- Só dá para sair disso achando o processo à mão. O `--restart` já falha, mas com a mensagem seca "host answered 401".

O `/health` exige token (`host-routes.js`), então nada na `main` consegue descobrir quem é o dono da porta.

## 3. Objetivo
Um host de outro checkout nunca fica invisível: o harness diz de qual pasta ele é e como resolver, e cada checkout usa a sua porta, então a colisão deixa de acontecer por padrão.

## 4. Requisitos
**Funcionais**
- RF1. **Porta por checkout.** O checkout principal mantém 4322. Outro checkout (worktree) usa uma porta própria derivada do caminho da raiz, estável entre execuções, na faixa 4400 a 4499. `HARNESS_ENGINE_HOST_PORT`, quando definido, vale sempre (testes usam `0`). `hostPort()` continua sendo o único lugar que decide, para servidor, host e CLI concordarem. A detecção do principal usa `isMainCheckout` (`tools/lib/ui-dev-guard.js`); se o git não responder, vale 4322 (comportamento de hoje).
- RF2. **Identidade sem token.** `GET /identity`, só loopback como as demais rotas, responde `{ app: "harness-engine-host", pid, startedAt, checkout }`, com `checkout` sendo só o nome da pasta da raiz. Nunca o caminho completo, o token ou a contagem de execuções.
- RF3. **Erro que orienta.** Quando o `/health` responde 401, `ensureHost` consulta `/identity` e a mensagem passa a dizer: "Já existe um host de motores da pasta `<checkout>` (pid `<N>`) nesta porta. Pare-o dentro dessa pasta (`npm run host:stop`) ou encerre o processo `<N>`." Sem `/identity` (host antigo), a mensagem diz que o dono é desconhecido e cita a porta.
- RF4. **Parada que diz a verdade.** `--stop` só imprime "stop requested" quando o host respondeu 200. Com 401 ele sai com código 1 e a mesma orientação do RF3. `--restart` troca "host answered 401" pela mesma mensagem.
- RF5. O contrato HTTP do chat para o navegador não muda.

**Fora de escopo**
- Encerrar o processo de outro checkout automaticamente (decisão do usuário, nunca do harness).
- Seletor de host local e VPS (23.06).

**Não funcionais**
- Arquivos até 250 linhas; a regra da porta é uma função pura (`checkoutPort(root, isMain)`) em módulo próprio, sem I/O.
- `/identity` nunca expõe dado que o `/health` protege.

## 5. Implementação
1. Função pura `checkoutPort` com hash estável do caminho para 4400 a 4499; `hostPort()` a usa quando a variável de ambiente não existe.
2. Rota `/identity` antes do teste de token, depois da checagem de loopback.
3. `ensureHost` e o texto de `HostUnavailableError` com a identidade.
4. `stopRunningHost` e `restart-cli` tratam 401 com a mesma mensagem.
5. `SETUP.md`: portas por checkout e como forçar a 4322 (`HARNESS_ENGINE_HOST_PORT=4322`, o rollback).
6. Linhas no mapa do host.

## 7. Critérios de aceite
- [x] CP-01 a CP-04 verdes, com o teste de CP-02 vermelho antes da correção.
- [x] Subir `npm run ui` num worktree e outro na `main` ao mesmo tempo, cada um com o seu host, sem erro de token. (Verificado com o host do worktree na 4462 enquanto um host real de outra pasta ocupava a 4322; o `npm run ui` da `main` não foi iniciado para não mexer no ambiente do usuário.)
- [x] `SETUP.md` descreve as portas e o rollback.

## 8. Riscos
- **Colisão na faixa 4400 a 4499:** outro programa pode ocupar a porta derivada. O host já recusa com "porta em uso"; `HARNESS_ENGINE_HOST_PORT` resolve. Aceitável para uma faixa de desenvolvimento.
- **Host antigo em execução durante a troca:** ele não tem `/identity`; o RF3 cobre com a mensagem de dono desconhecido.
- **Rollback:** `HARNESS_ENGINE_HOST_PORT=4322` volta ao comportamento atual.

## 9. Evidências
- Testes: `tests/engine-host-checkout.test.js` (8): CP-01 a CP-04 e a regra da porta (CP-05). Sem o código novo falham CP-01 (2 testes), CP-02 e CP-04; com ele os 8 passam, e os 12 testes que já existiam do host seguem verdes.
- Verificação real: o host de um worktree subiu na 4462 enquanto um host real, de outra pasta, ocupava a 4322. `ensureHost` funcionou, `/identity` respondeu `{ checkout: "ep-21-03", pid, startedAt }` e `--stop` encerrou só o dele.
- Achado: um host anterior a esta história responde 401 (e não 404) a `/identity`, porque o token é checado antes da rota. O cliente trata qualquer resposta que não seja 200 como dono desconhecido, e o teste usa esse comportamento.
- **Pendente:** o host que já está rodando na 4322 usa o código antigo e só responde `/identity` depois de reiniciar (`npm run host:restart`, que espera as respostas em andamento).
