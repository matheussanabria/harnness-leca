# EP-25.02: Contexto de escopo explícito e workspace pessoal

## 1. Identificação
- **Épico:** [EP-25](README.md)
- **Prioridade:** P0
- **Dependências:** 25.01
- **Bloqueia:** 25.03, 25.05, 25.06

## 2. Contexto
`projects/.active` é lido por cerca de 20 serviços (`project-selection.service.js`, `project-scrum-*`, `prototype-*`, `usage-ingest`, `agent-activity` e outros). Duas janelas não podem ter projetos diferentes e não existe lugar para o que não pertence a projeto algum.

## 3. Objetivo
Cada requisição resolve um `scope = { projectSlug | null }` explícito; `null` aponta para o workspace pessoal `projects/_pessoal/`. O `.active` vira só o "último projeto usado".

## 4. Requisitos
**Funcionais**
- RF1: resolvedor `resolveScope(req)` lê o projeto do cabeçalho `X-Harness-Project` ou do parâmetro de rota, e cai no `.active` só como padrão do seletor.
- RF2: criar `projects/_pessoal/` na primeira necessidade, com a mesma estrutura de um projeto (instruções, `chats/`, `context/`).
- RF3: o slug `_pessoal` é reservado: não pode ser criado, arquivado nem listado entre projetos comuns.
- RF4: memória no escopo pessoal usa apenas a global; nenhuma memória de projeto é injetada.
- RF5: migrar o primeiro serviço (chat) para receber o escopo, sem mudar o contrato HTTP.

**Não funcionais**
- Serviços `project` continuam lendo o `.active` até migrarem; nada quebra.
- Escrita atômica do `.active` mantida. Limite de 300 linhas por arquivo.

## 5. Arquitetura
`ui/server/scope/` com `resolve-scope.js`, `personal-workspace.js` e um middleware que injeta `req.scope`. Decisão em ADR-019 itens 2 e 3. O hook `load-project.ps1` deixa de assumir que sempre há projeto.

## 6. Implementação
1. Testes do resolvedor (cabeçalho, rota, padrão, slug reservado).
2. Implementar resolvedor e workspace pessoal.
3. Injetar o middleware no roteador e expor o escopo ao cliente.
4. Migrar o serviço de chat e provar que o contrato HTTP não mudou.
5. Atualizar o mapa e registrar no `exec-log`.

## 7. Testes
| Tipo | Cenário | Comando ou arquivo |
|---|---|---|
| Unitário | cabeçalho vence `.active`; `_pessoal` reservado | `node --test tests/scope-resolve.test.js` |
| Integração | chat sem projeto grava em `_pessoal` | `node --test tests/scope-chat.test.js` |
| Regressão | chat com projeto continua idêntico | `npm test` |

## 8. Critérios de aceite
- [ ] Duas requisições com projetos diferentes não interferem entre si.
- [ ] Chat sem projeto cria e usa `projects/_pessoal/`.
- [ ] Nenhum serviço migrado lê o `.active`.
- [ ] `_pessoal` nunca aparece na lista de projetos.

## 9. Riscos
- Serviço que lê o `.active` indiretamente por `config.js`: mapear todos antes de migrar (lista em evidências).
- Hook de contexto assumindo projeto: testar com `.active` vazio.

## 10. Evidências
Implementada em 2026-11-23 (rota completa), aguardando aceite.

- Código: `ui/server/scope/` (reserved, personal-workspace, resolve-scope); `config.js` (`slugs()` oculta slugs reservados); `tools/lib/state.js` (aceita `_pessoal` e `HARNESS_PROJECTS_DIR`); validadores do chat em `chat.controller.js`, `chat-conversations.controller.js` e `engine-host/run-starter.js`.
- Testes: `tests/scope-resolve.test.js` e `tests/scope-chat.test.js`; suíte completa com 2982 passando e 0 falhas.
- Ainda leem o `.active` (migram na vez de cada funcionalidade): `ui/server/config.js` (`active()`), `overview.controller.js`, `project.controller.js`, `project-selection.service.js`, `project-screens-fallback.js` e as ferramentas `tools/adopt-project.js`, `coordination.js`, `daily-journal.js`, `ds-sync.js`, `jira-query.js`, `jira-refresh.js`, `lib/hia/registry.js`, `lib/memory/run-lint.js`, `memory.js`, `suggest-groups.js`.
- Em aberto: o cliente ainda não envia `X-Harness-Project` nem oferece "Sem projeto" (história 25.05); a memória do escopo pessoal usa só a global por convenção (o `memory.md` de `_pessoal` fica vazio), sem trava no hook de contexto; o middleware que injeta `req.scope` ficou de fora, cada serviço chama `resolveScope` quando migra.
