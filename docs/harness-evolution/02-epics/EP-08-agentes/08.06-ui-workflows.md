# EP-08.06: Workflows UI: catalog, plan and runs

[Back to the epic](./README.md)

## 2. Context
EP-08.04 exposes the workflow catalog, the per-project plan and the run lifecycle. EP-08.05 added the Rotinas tab (`ui/public/js/modules/design-routines*.js`), the only place in `ui/public/` that talks to the orchestration backend today. There is no UI for the workflow catalog, the plan or the runs: the user cannot see which agent owns an SDLC stage, which project skills exist or are missing, the gate/permissions of a stage, or start and follow a workflow run.

Verified shapes before writing this story:
- `GET /api/orchestration/workflows` returns `{ workflows: [{ id, label, description, stageCount }] }`.
- `GET /api/project/:slug/workflow-plan/:workflowId` returns `{ ok, slug, workflowId, laneId, workflow, stages[], totals, warnings }`; each stage has `id`, `label`, `order`, `executors`, `agents[{ id, label, role, required, builtin }]`, `skills[{ name, key, available, bound }]`, `writes`, `gate`, `mode`, `permissions{ read, write, exec }` and `requiresApproval`.
- `POST /api/project/:slug/workflows/:workflowId/runs` accepts `{ dryRun, actor, laneId, idempotencyKey }`; a dry run returns `{ ok, dryRun: true, plan }`, a real start returns `{ ok, dryRun: false, idempotent, run }`, and non-loopback requests return `403` with `{ error }`.
- `GET /api/orchestration/workflow-runs?slug=` returns `{ runs: [{ executionId, workflowId, status, currentStage, stages, totals, ... }] }`.
- `POST /api/orchestration/workflow-runs/:executionId/advance` and `/cancel` return `{ ok, run }` or an error with `{ error }`.

## 3. Objective
Give EP-08 a user interface: a new **Workflows** tab in the design workspace that lists workflows, shows the stage plan with the responsible agents, project skills, gates, permissions and missing items, starts a run (or a dry run) and lists the project runs with Advance and Cancel actions.

## 4. Requirements
**Functional**
- RF1: add a `workflows` view to the design workspace nav, next to `routines`, wired through `ui/public/index.html` and `ui/public/js/modules/design.js`.
- RF2: list workflows from `GET /api/orchestration/workflows`; selecting one loads `GET /api/project/:slug/workflow-plan/:workflowId` for the active project.
- RF3: render the plan stages in `order`, showing the responsible agent, project skills (available/missing), gate, approval requirement and permissions.
- RF4: show loading, empty and error states for the workflow list, the plan and the runs list.
- RF5: a Start button calls `POST /api/project/:slug/workflows/:workflowId/runs`; a "dry run" checkbox sends `dryRun: true` and renders the returned plan without starting anything.
- RF6: when the start refuses (loopback-only `403` or validation error), show the server error text.
- RF7: list runs from `GET /api/orchestration/workflow-runs?slug=` filtered by the active project, with status and current stage.
- RF8: Advance and Cancel buttons call `POST /api/orchestration/workflow-runs/:executionId/advance` and `/cancel`, show errors and refresh the list.
- RF9: agent names and stage labels come from API data; all API text is escaped before rendering.

**Non-functional**
- Files at 300 lines or fewer, separating HTTP, state, view and DOM orchestration.
- FontAwesome icons only; no emoji; no `window.confirm`, `alert` or `prompt`.
- No backend file changes.
- No regression in the Rotinas tab, the design workspace or the 2.5D interface.

## 5. Architecture
```
[design-workflows-api.js]   HTTP client for workflows, plan, start, runs, advance and cancel
          |
[design-workflows-state.js] reducer + initial state for list/plan/runs/dry-run statuses
          |
[design-workflows-view.js]  pure HTML renderers (workflow cards, stages, runs) with esc()
          |
[design-workflows.js]       loads data, binds DOM events, refreshes after actions
          |
[27-workflows.css]          panel, catalog, action bar and runs table
[28-workflows-plan.css]     plan, stages and skills (split to stay under 300 lines)
```

The Workflows tab has no new hash route: the screen registry is server-side (`ui/server/services/screen-state/registry.js`) and this story does not change backend files. `persistDesignView` still saves the view for restore, but it only writes a route when the view belongs to `VIEW_SCREENS`; selecting Workflows therefore does not redirect the address bar.

## 8. Acceptance criteria
- [x] A Workflows tab exists next to Rotinas and opens from the design workspace.
- [x] The tab lists the catalog workflows and loads the plan when one is selected.
- [x] The plan renders stages in order with agent, skills, gate, permissions and missing items.
- [x] Empty, loading and error states are visible for list, plan and runs.
- [x] Start sends the run request; dry run sends `dryRun: true` and renders the returned plan.
- [x] A refused start shows the server error text.
- [x] The runs list shows status and current stage for the active project.
- [x] Advance and Cancel call their endpoints and refresh the list.
- [x] All text from the API is escaped; agent and stage names are not hard-coded.
- [x] FontAwesome only, no emoji, no window.confirm/alert/prompt.
- [ ] Browser-only acceptance: manually open the tab, select both workflows, start a dry run, start a real run and use Advance/Cancel. (Not exercised by the plain-node test suite; see Evidence.)
- [x] New files stay at 300 lines or fewer and `npm run check` passes.

## 9. Risks
- **Compatibility:** the tab is additive; the Rotinas tab and existing design views are untouched.
- **Security:** start, advance and cancel are loopback-only on the server; the UI only displays the server error when refused.
- **State:** runs live in server memory; a restart empties the runs list (same behavior as the backend).
- **Rollback:** removing the tab, its modules and the CSS import returns the UI to the EP-08.05 state; no backend file changed.
