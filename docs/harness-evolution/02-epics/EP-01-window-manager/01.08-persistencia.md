# 01.08: Persistência e restauração

## 1. Identificação
- **Épico:** [EP-01](README.md)
- **Prioridade:** P0
- **Dependências:** 01.06
- **Bloqueia:** 01.09, 01.10

## 2. Contexto
No estado inicial do escritório virtual, qualquer recarregamento da página (`F5`), navegação ou troca de contexto descarta a disposição de janelas organizadas pelo desenvolvedor. Além disso, a auditoria do EP-00.03 identificou que persistências anteriores no `localStorage` careciam de identificadores de versão (`_v`), arriscando corrupções de estado caso o modelo de dados mudasse entre releases.

## 3. Objetivo
Implementar o `LayoutPersistenceManager` para serializar o layout completo do `WindowManager` com controle estrito de versão de schema (`_v: 1`), namespace isolado por projeto, sanitização geométrica ao restaurar em viewports alterados e descarte seguro de formatos antigos ou corrompidos.

## 4. Requisitos
**Funcionais**
- RF1: Função pura `serializeLayout(store, metadata)` que extrai snapshot imutável com `_v: 1`, timestamp, `projectId` e lista sanitizada de janelas abertas (bounds, presentation, visibility, dock, moduleId).
- RF2: Função pura `deserializeLayout(payload, validatorOptions)` que valida a integridade do payload, confina os limites das janelas ao viewport atual (`constrainBounds`) e ignora módulos inexistentes no catálogo.
- RF3: `LayoutPersistenceManager` com suporte a chave namespaced (`dai:wm:layout:<projectSlug>`), debouncing para evitar excesso de I/O no `localStorage` e tratamento resiliente de erros (quota exceeded / storage desabilitado).
- RF4: Migração/fallback seguro: payloads com versão de schema desconhecida ou inválida devem ser descartados sem gerar exceções em runtime.
- RF5: Capacidade de redefinir o layout para o estado de fábrica (`resetLayout(projectSlug)`).

**Não funcionais**
- Arquivos estritamente abaixo do limite de 250 a 300 linhas (`layout-persistence.js` < 220 linhas).
- Zero uso de emojis; apenas ícones FontAwesome em notificações ou botões visuais.
- Não regressão no modo 2.5D nem no painel tradicional.
- Cobertura de testes unitários abrangente via `node --test`.

## 5. Arquitetura
- **Módulos:**
  - `ui/public/js/window-manager/layout-persistence.js`: lógica pura de serialização, validação de schema, sanitização e persistência.
- **Contratos:**
  - `LayoutPayload`: `{ _v: number, updatedAt: number, projectId: string, windows: SerializedWindow[], activeWindowId: string | null }`
  - `serializeLayout(state, metadata)` -> `LayoutPayload`
  - `validateAndSanitizeLayout(payload, viewport)` -> `LayoutPayload | null`
  - `LayoutPersistenceManager`: `{ save(projectSlug), restore(projectSlug, viewport), clear(projectSlug) }`

## 6. Implementação
1. Criar `ui/public/js/window-manager/layout-persistence.js` com funções puras de serialização, validação de schema `_v: 1` e confinamento ao viewport.
2. Criar a suíte unitária `tests/layout-persistence.test.js`.
3. Integrar os testes e atualizar `MAPA.md`.

## 8. Critérios de aceite
- [x] Schema versionado `_v: 1` gerado em toda serialização.
- [x] Payloads corrompidos ou sem versão válida são descartados com log de aviso sem quebrar a tela.
- [x] Janelas salvas em tela grande têm suas coordenadas confinadas suavemente ao restaurar em viewport menor.
- [x] Layout isolado por projeto (`dai:wm:layout:<projectSlug>`).
- [x] 100% dos testes unitários passando.

## 9. Riscos
- **Compatibilidade:** Funciona de forma transparente em browsers com ou sem `localStorage` ativo.
- **Segurança:** Dados sanitizados antes de aplicar; impossibilidade de injeção de scripts no DOM a partir de storage.
- **Rollback:** `clearLayout` remove a chave e restaura o posicionamento padrão das estações.
