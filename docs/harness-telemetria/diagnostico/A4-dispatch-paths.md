# A4 - Dispatch paths: where sessions, agents, subprocesses, skills and workflows are born, run, stop and end

Scope: read-only diagnosis for sections 4, 5, 7, 8 and 13 item 3 of `docs/harness-telemetria-resumo-executivo-pre-plano.md`.
Method: read MAPA.md, `docs/mapa/02`, `10`, `13`, then targeted reads and greps of `ui/server/` and `tools/`. Labels: **V** = verified in code (file:line read), **A** = assumption (not opened or inferred).

## 0. Headline findings

1. **Two separate event systems exist and nothing bridges them (V).**
   - Orchestration `eventEngine` (`ui/server/services/orchestration/event-engine.js:112`): in-memory singleton, history capped at 1000 (`:14`), lost on restart. Fed by `emitWorkflowEvent` (`workflow-events.js:8`).
   - EP-09 `event-store` (`ui/server/services/events/event-store.js:117 appendEvent`): SQLite, per project, cursor, idempotent. Reached only through `publish()` (`event-stream.js:92`).
   - `grep` for `event-store|event-stream|publish(` across `ui/server` and `tools` shows only two callers of `publish`: `central-events.controller.js:109` (loopback `POST .../events`) and `session-registry-orchestrator.service.js:23` (`session.discovered`). No chat, engine, workflow, routine, sync or approval code publishes to the EP-09 store.
2. **Engine subprocess spawns happen with zero identity propagation (V).** The chat path generates `chatId = crypto.randomUUID()` (`chat.controller.js:110`) but it is used only for permission cards and the shadow correlation id; it is never persisted as an execution id and never put in an event.
3. **Workflow runner has the richest ids (V)**: `executionId = wf-<uuid>` (`workflow-runner.service.js:56`), `stageId`, `taskId = stage:<id>`, `idempotencyKey`, `routineId`, `laneId`, `actor`. But the workflow runner does **not** spawn an engine: stages are advanced by an external caller via `advanceWorkflowRun`. So "who executed this stage" (agent, session) is not linked (V: no engine/sessionId field in the run object, `:55-80`).
4. **Skill use has no runtime evidence in the harness (V).** Skills are only discovered/listed/bound; nothing records that a skill was loaded by an engine run.
5. **No attempt/retry concept exists** in the workflow runner (V: no `attempt` field; a failed stage ends the run, `:182-191`).

## 6. Ranked instrumentation points (top 5)

One edit sends every workflow, stage, approval, cancel and routine event (2.1-2.5, 4.5, 4.7) to the EP-09 store with real ids (`executionId`, `taskId`, `actor`). Lowest cost, highest coverage of ids already generated server-side. Keep the in-memory ingest.

Mint one `runId` (reuse `chatId`) and emit `run.started`, `run.finished`, `run.errored`, `run.cancelled`, `run.rejected` for every engine at once, including HIA script/local routes (1.1, 1.2, 4.6, 4.9). Emit `process.spawned {pid}`, exit code/signal, real engine `sessionId`, and `session.resumed`. Must also fix `ollama` fixed `"ollama-local"` id and Codex non-tree kill (1.3-1.7, 4.3).

## 7. Blocking questions

1. **Which store is canonical for telemetry?** The in-memory `eventEngine` (orchestration, 1000 events, lost on restart) and the SQLite EP-09 store coexist with overlapping event vocabularies (`execution.*`, `task.*` vs `session.*`; EP-09 has "aliases de tipo", `docs/mapa/13`). Is the intent to make EP-09 the sole persisted source and treat `eventEngine` as a live cache? Need the EP-09 type vocabulary (`event-contract` of EP-09 vs `orchestration/event-contract.js`) reconciled before bridging (not compared in this pass: A).
2. **What is the id model?** Chat `chatId` (uuid), engine `sessionId` (engine-owned, can change on resume/recreate), canonical `session.id` (fingerprint), workflow `executionId`. There is no attempt/retry id and no agent-run id. Which one is the primary correlation key, and who mints `attemptId`?
3. **Cancel semantics.** Is it acceptable to treat `res.on("close")` before finish as `cancelled`, or is a distinct stop endpoint required for an honest user-cancel vs disconnect distinction (also relevant to remote/tunnel 524 cases noted in `chat.controller.js:99`)?
4. **Subagent/skill evidence source.** Claude's stream-json block shapes for `Skill`/`Task` were not verified here (A). Should evidence come from the live stream parser, from post-hoc JSONL import (which currently skips sidechains), or both? Codex/Gemini/OpenCode/Ollama have no equivalent signal in the adapters (V: none parsed), so skill-use telemetry would be Claude-only unless those are accepted as "unknown".
5. **Who advances workflow stages?** The runner never launches an engine; `advanceWorkflowRun` is called by some external actor (UI or agent, not traced in this pass: A). Without knowing the caller, stage-to-agent attribution cannot be made non-self-reported.
6. **Scope of non-agent subprocesses.** Should deploy/health/audit/dev-service spawns (1.16, 1.17) and the legacy `tools/lib/routines.js` runner be in the telemetry scope, or only agent-related paths? Two routine systems exist (legacy `scheduled/*.md` vs EP-08.05) and only the latter is tied to workflow ids.
7. **Privacy of prompts.** Prompts and history flow through every spawn site (e.g. `claude.js:34-38`); the event payload policy (hash vs length vs none) must be fixed before adding publishers.
8. **Not opened in this pass (A):** `orchestration/adapters/*`, `tools/lib/runtime/shadow.js`, `tools/lib/hia/telemetry.js` schema, `tools/lib/engines/index.js saveChatToProject`, `orchestration.controller.js`, `event-contract.js` files, the callers of `advanceWorkflowRun`.
